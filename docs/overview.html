01问题：知识沉淀为什么一直失败

不是没人想写文档，是既有的三条路都走不通。

一个跑了很多年的业务系统，真正的业务规则散在几十万行代码、几百张表、 上千次提交里。接手的人——不论是新同事还是 AI——面对的都是同一件事： 没有任何一份材料告诉你「这个系统在做什么业务」。 常见的三种补救，各自在不同的地方断掉：

做法为什么在老项目上失效
人工补文档 成本按人月计；写完当天就开始腐烂——没有任何机制让它跟着代码变。半年后没人敢信它。
自动生成调用图 / 类图 产出的是结构不是业务。「A 调 B 调 C」回答不了「这条链路在处理什么业务、有什么坑」。而且老项目一律面向接口编程，纯语法调用图会死在接口边界。
把代码丢进向量库做 RAG 检索出的片段无结构、无边界，模型只能顺着片段编。没有证据锚点，幻觉不可检测；代码一改，索引整体失效，也说不清哪条结论该作废。

三条路的共同病根是同一个：把「事实」和「叙述」混在一起。 人工文档全是叙述、没有事实锚点；调用图全是事实、没有叙述；RAG 则是拿事实碎片 现场编叙述，二者的坏处都占了。

02核心洞察：可靠知识藏在哪

在老项目上做了实证，然后把整个工具建在这个结论上。

老项目里最可靠的业务知识不在代码结构里。代码结构反映的是当年的技术选型， 经过多轮重构和人员更替，早已不对应业务划分。真正稳定的业务信息集中在三处：

① 中文注释，尤其是枚举与常量类

PromotionTypeEnum.TEJIA("特价活动") 这样的一行，同时给出了 业务术语、代码标识符、取值枚举三重信息。这是老项目里信息密度最高的地方—— 因为写它的人是为了自己以后看懂，而不是为了交差。

② 表结构与表访问

数据模型比代码稳定得多：字段名、字段注释、哪个 DAO 读写哪张表， 刻画的是业务实体本身。目标项目往往连 DDL 都没有，但 MyBatis 的 resultMap 能把表和字段完整反推出来。

③ git 历史

提交信息里是当时的业务语境（「新增砍价活动」「修复优惠券叠加」）， 分支名是业务词表，而「哪些文件总是一起改」是比包结构更真实的业务边界信号。

这三处有一个共同性质：都能被确定性地抽取——不花 token、可复现、 同样的输入永远得到同样的输出。这个性质是后面所有机制的地基。

03核心机制：三层知识模型

把「事实」和「叙述」严格分层，叙述必须挂证据。

整个工具的骨架就是下面这个分层。每一层只消费下一层的产出， 成本、可靠性、失效方式都不同：

零 token · 秒级 · 完全可复现 L0证据层 —— 确定性抽取

从源码、配置、git 里扒出不会出错的事实：Maven 模块树； tree-sitter 解析出的类/方法/字段/枚举成员（含 Javadoc 原文与行号）； mapper XML 反推的表与字段；哪个 DAO 读写哪张表； Dubbo 接口 / HTTP 路由 / XXL-Job 任务 / MQ 消费者这四类入口清单； 带置信度的调用边；每文件的 churn、触碰它的提交 subject、分支词表。

↓ 纯计算推导，不引入新信息

零 token · 纯计算 L1结构层 —— 确定性推导

领域划分：包路径、表名前缀、git 共变、调用关系四路信号加权投票， 迭代传播到不动点，把几十万行代码切成若干业务领域。
能力链路 trace：从每个入口沿调用边 BFS 下探， 到触表的符号终止——得到「这个接口最终动了哪些表」的完整链路。

↓ 证据打包 → 大模型只做「解读」，不做「检索」

按需花 token · 逐条挂证据 L2叙述层 —— LLM 生成

术语表：中文业务术语 ↔ 定义 / 别名 / 代码标识符。
领域档案：职责、核心概念、生命周期与状态机、业务规则、⚠️ 已知陷阱、待确认问题。
能力叙述：单个入口的调用者视角——入参含义、执行过程、副作用、约束、易踩的坑。

这个分层直接换来三个性质： L0/L1 免费且可复现，所以全量骨架可以零成本先铺满； L2 的每一条都挂着 L0 的证据，所以可追溯、可审计； 证据变了就知道哪一条该重算，所以可增量演进。

两段式：先铺满，再深挖

因为 L0/L1 不花钱，工具的使用方式是两段式的： catlas init 先在几十秒内把全项目骨架铺满——模块、符号、表、入口、领域、链路全都有了， 一个 token 都没花；之后再按需对某个领域或某个入口花 token 深挖业务语义。 贵的部分永远是可选的、按需的、可估算的（--dry-run 先报预估 token）。

04让叙述可信的三个装置

LLM 写的东西默认不可信——所以给它套上三重约束。

① 证据包 + 硬约束 prompt：让模型只能解读，不能检索

模型拿到的不是「一堆代码片段」，而是 L0/L1 组织好的结构化证据包， 按信息密度排序裁剪到预算内：枚举注释 > 表结构 > 入口 > 链路 > 提交信息 > 源码节选。 跨领域共享的类型（比如一个被到处引用的 PromotionTypeEnum）会被显式标注，避免误归到某个领域。 system prompt 里是硬约束：只依据给定证据、不确定必须写 UNKNOWN、 区分「代码行为」与「业务意图」、只输出 JSON。

② source_digest：证据变了，结论自动失效

每条 L2 记录强制持有一个 source_digest——它所依据的那批证据的摘要——外加一个 status。重建时重算 digest：不变则这条结论仍然新鲜，跳过； 变了则标记为过期待重算；依据的领域整个消失了，则标记为 stale 而不是错误地继续渲染。 这是「文档不腐烂」的机制保证：陈旧的结论不会沉默地留在文档里冒充有效。

③ 稳定键 relink：重建数据库不丢已有结论

全量重建会让所有行的 id 重新分配。如果 L2 笔记按 id 挂载，一次重建就全成孤儿。 所以笔记挂的是稳定的业务键（domain_key / subject_key）， 重建后按键重新链接。已验证的三条路径：重建后笔记存活并正确重链； 新领域插入导致 id 漂移（coupon 从 1 变 2）后笔记跟着重链； 领域被人工排除后其笔记转为 stale。

存储：SQLite 是唯一真相，Markdown 只是视图

所有事实与结论都在 .codeatlas/codeatlas.db 里，程序可查询、可增量更新； .knowledge/ 下的 Markdown 是 render 派生出来的视图，可以随时删掉重建。 这样人读 Markdown、程序查 SQLite、agent 走 MCP，三方消费同一份真相，不会各自漂移。 项目的 CLAUDE.md 只被写入一个带标记的托管块，块外的手写内容一律不动。

05关键难点与解法

在真实老项目（12 模块 / 23 万行 / 5003 commit / 零文档）上撞出来的问题。

包结构不是业务边界 → 四路信号加权投票

老项目的包结构早被重构揉烂了，不能直接当领域。所以领域划分用四路信号投票： 包路径（权重 3）、表名前缀（2）、git 共变（1）、调用关系（1）， 迭代传播到不动点。配套两个必要的修正：

  • 同义拼写折叠：groupBuying / groupbuying / group_buy 是同一个领域，不折叠就碎成三个。
  • 命名空间自动识别：com/company/product 这样在同一路径深度出现率 ≥90% 的段是命名空间，不是领域——按出现率识别，而不是硬编码公司名。

划分结果可以被 .codeatlas/domains.toml 人工覆盖，人工优先级最高。

调用图死在接口边界 → 补 override 边

老项目一律「经接口调服务」。纯语法调用图走到接口方法就断了， 根本到不了实现类、更到不了数据表。补上「接口方法 → 实现方法」的 override 边之后， 在实测项目上可用链路从 4 条变成 455 条——这是从「不可用」到「可用」的差别。 调用边解析不了的情况不丢弃，降级存原始文本并标低置信度（1.0 / 0.6 / 0.3 三档）。

朴素表名提取会凭空造表 → 特判 SQL 陷阱

MySQL 的 ON DUPLICATE KEY UPDATE col 会骗过朴素的表名提取器， 让 col 被当成一张表。这类特判必须做，否则知识库里会混进不存在的表—— 一个凭空造出来的事实，比缺失的事实伤害更大。

中文检索：trigram 分词

SQLite FTS5 默认的 unicode61 按空格分词，对中文完全失效。 改用 trigram 分词后中英文都按子串匹配。代价是 ≤2 字符的查询不命中（比如「特价」两个字）， 所以短查询自动回退到 LIKE 子串扫描——只在短查询时触发，代价可控。

增量同步：为什么不看 git 提交记录

catlas sync 判断「哪些文件变了」用的是每个文件内容的 SHA-256，而不是 git log。 这是个反直觉但必要的选择：

  1. git 看不见未提交的改动。开发最频繁的循环是「改一行 → 跑一次看效果」，而 git log 只反映已提交状态，恰好漏掉这个循环。
  2. git 记录的是「哪个 commit 碰了哪些文件」，不是「磁盘字节与上次索引时是否不同」。文件被 revert 回原样、rebase 重写了对象、换台机器重新 clone——commit sha 都指不到「上次解析的那个字节状态」。
  3. 代价不对称。git log 全量走历史是整个构建里最慢的一步；而对几千个文件做 sha256 单线程都不到一秒。

而 sync 真正的难点根本不在「找变更文件」，在于 L1/L2 是全局聚合： 调用边解析需要全项目符号表、领域投票需要全局信号、trace BFS 和检索索引都无法按文件增量。 所以解法是复用整条构建流水线，只跳过 tree-sitter 解析这一步—— 未变更文件的解析结果按内容哈希缓存，命中即复用， 产出与全量构建逐字节一致。工具版本升级（语法树或 schema 变了）时丢弃缓存全量重算。 git 历史信号则做了三级缓存：HEAD 没动直接复用，HEAD 前移走 old..new 增量折叠， rebase/force-push 后回退到全量 walk——增量结果与全量 walk 实测逐字节一致。

还有一条：让 AI 直接用

知识库不只给人看。catlas mcp 以 MCP server（stdio JSON-RPC）方式运行， 向 Claude Code 暴露三个只读工具——search（全文检索）、domains（领域清单）、 status（各层统计）。注册一行即可：

于是 AI 接手老项目时，不再是「在几十万行里硬啃」， 而是先问知识库「这个项目有哪些业务领域」「『砍价』相关的代码和表在哪」， 拿到带证据的结构化答案再动手。

07为此做了哪些事

四个阶段，全部实现并验证。

阶段 A —— 骨架与 L0 证据层 已完成

  • SQLite schema 与迁移；所有表带 project_id（为跨项目融合预留）
  • Maven POM 模块树
  • Java 符号抽取（tree-sitter，rayon 并行）：类/接口/枚举/枚举成员/方法/字段/常量 + Javadoc + 注解
  • MyBatis mapper XML → 表/字段/表访问（含 @TableName、ON DUPLICATE KEY UPDATE 特判）
  • Dubbo XML → 服务入口；Spring XML → MQ 消费者；@XxlJob → 定时任务；Spring MVC 注解 → HTTP 路由
  • 调用边解析（import + 字段类型启发式，带 confidence，解析失败降级存原文）
  • git 历史信号：churn、提交 subject、分支词表

阶段 B —— L1 结构层 已完成

  • 领域划分：四路信号加权投票 + 变体折叠 + 命名空间识别 + domains.toml 人工覆盖
  • 入口→数据表链路 trace：BFS（深度 ≤6），含接口→实现的 override 动态分发边
  • Markdown 渲染：README / 领域档案 / 术语表 / 参考清单（tables、entrypoints、jobs、mq）+ CLAUDE.md 托管块

阶段 C —— L2 叙述层 已完成

  • LLM client：直连 Messages API（复用 $ANTHROPIC_BASE_URL / $ANTHROPIC_AUTH_TOKEN），凭证文件隔离
  • 证据包按预算裁剪，跨领域共享类型显式标注
  • 领域档案 + 术语表生成，含解析失败重试与截断检测
  • prompt 级缓存：按 prompt+model+max_tokens 哈希命中，只缓存解析成功的响应（坏响应不固化）
  • capability：单入口能力叙述，渲染进入口参考页

阶段 D —— 增量与 agent 接入 已完成

  • L2 结论跨重建存活：稳定键 + relink，三条路径端到端验证
  • 按 digest 失效，--only-stale 跳过仍新鲜的结论
  • catlas query：FTS5 全文检索，trigram 分词，短查询 LIKE 回退，支持 --json
  • catlas sync：sha256 变更检测 + 解析缓存复用 + git 信号三级缓存
  • catlas mcp：stdio JSON-RPC MCP server，三个只读工具

可复用性：probe 架构

抽取引擎是一组可插拔的 probe（detect 判定适用性 + extract 抽取）， 当前实现 maven / java / mybatis-xml / spring-xml / dubbo-xml / properties / git。 换一种技术栈的老项目（Spring Boot 注解式、MyBatis 注解式，乃至其它语言） 只需新增一个 probe，核心流水线与 schema 不动。

09现有机制的缺点与优化方向

上面讲的是机制成立的地方，这节讲机制本身的代价——按影响面排序。

第 08 节的「边界」列的是还没做的功能；这一节列的是已做部分本身的缺陷—— 即使功能都做了，下面这些问题依然存在，因为它们来自设计权衡而不是工作量。

一、L0 的准确性天花板：启发式调用解析

影响大 调用边靠启发式而非真正的类型推导，链路会静默缺失

调用边的置信度是启发式打出来的：接收者是已知声明类型的字段且该类型声明了此方法 → 1.0； 类型已知但方法不在其上（继承来的）→ 0.6；只知道方法名、且全项目恰有一个类型声明它 → 0.3。 而 trace 构建时会丢掉 0.6 以下的边。这意味着三类调用会静默消失： 局部变量接收者、泛型/容器里取出的对象、以及反射与 Spring 动态代理。 实测 506 个入口只产出 455 条链路，缺口正来自这里——而且缺失是静默的， 文档不会告诉你「这个入口的链路没扒全」。

优化方向：①把「入口无链路 / 链路 min_confidence 低」显式渲染成警示， 让缺失从静默变可见，这是成本最低、收益最直接的一步； ②做方法体内的局部变量类型绑定（tree-sitter 已有 AST，属增量工作）； ③把 0.3 的弱边单独成一类「疑似链路」呈现而不是丢弃。

影响中 trace 的 MAX_DEPTH=6 与每入口 24 条路径是硬上限

老项目里「Controller → Service → Manager → 另一个 Service → DAO」这种层层转发很常见， 六层不一定够；超限即截断，同样没有标记。每入口 24 条路径的上限在扇出大的入口上会丢掉真实分支。

优化方向：触达上限时打标记（truncated），并允许按项目配置上限—— 比给一个更大的固定值更稳。

二、L1 的可解释性缺口：领域划分是个黑箱

影响大 四路投票的权重 3/2/1/1 是拍出来的，且划分结果不可解释

权重没有经过调参或交叉验证，是在一个项目上试出来的经验值；换一个包结构风格不同的项目 （比如按技术分层而非按业务分包）不保证还合适。更麻烦的是结果不可解释： 实测切出 43 个领域，但工具说不出「XxxService 为什么被归到 A 而不是 B」、 也不给置信度。用户只能全盘接受或手写 domains.toml 全盘覆盖，中间没有台阶。 43 个领域对 12 个模块的项目而言也偏碎——很可能有该合并的。

优化方向：①落一张投票明细表（每个符号各路信号的得票与最终归属）， 渲染时输出「归属理由 + 次优候选」，让人能针对性地只覆盖有疑问的那几个； ②给领域本身打内聚度分数，低分的标注「建议人工确认」； ③把权重提到配置里，并在多个项目上做一次对照，用数据而不是直觉定默认值。

三、L2 的根本局限：只能解读已存在的痕迹

影响大 证据里没有的业务知识，机制上永远补不出来

整套设计的基石是「叙述必须挂证据」——这挡住了幻觉，但同时划定了能力上限： 注释写错了会被如实当成事实沉淀（老项目里注释与代码不一致极常见， 而工具无法判断哪个才对）； 从未写进注释、也没在 commit 里留痕的业务规则（口头约定、只在需求文档或某人脑子里的东西） 根本无从抽取。所以它是把散落的知识聚拢，不是创造缺失的知识。

优化方向：①主动做矛盾检测——注释与代码行为不符、 枚举注释与实际取值不符时，产出「待确认冲突」清单，让工具从「沉淀者」升级为「提问者」， 这恰恰是最有价值的产出；②支持人工补充的知识条目与抽取结果同层存放并标注来源， 让口头知识有个能落下来的地方。

影响中 证据包按字符数截断，重要证据可能被挤掉

证据裁剪是「按固定优先级、各段填到字符预算为止」。同一段内部的取舍是顺序决定的， 没有重要性排序——一张核心业务表可能因为排在后面而被截断掉， 而前面填进去的可能是无关紧要的枚举。大领域尤其吃亏。

优化方向：段内按信号强度排序（churn 高、被引用多、在链路上的优先）， 并把预算单位从字符改成 token；对超大领域改为分批深挖后合并，而不是硬截断。

影响中 L2 质量只有人工抽查，没有回归基线

127 个单测覆盖的是确定性部分（抽取、解析、缓存、检索、MCP）； L2 的质量目前靠人工抽查一个领域。这意味着换模型、改 prompt、调证据包之后， 没有任何自动手段能判断质量是升了还是降了。

优化方向：建一套小规模「黄金集」——人工确认过的若干领域结论， 作为 prompt/模型变更的回归基线；再加机械校验：叙述里提到的表名、枚举值、标识符 必须都能在 L0 里查到，查不到就是幻觉，可自动判定。

四、增量机制的残留成本

影响中 sync 只免掉了 tree-sitter，全局聚合每次都要重算

改一个文件，调用边解析、领域投票、trace BFS、检索索引重建依然全量跑一遍。 在实测规模（1714 文件）上全量才 20 秒，所以现在不痛； 但这是与项目规模线性相关的固定成本，换到十倍大的库就会变成体验问题。 检索索引每次整体 wipe+refill 也属于同类浪费。

优化方向：先按规模决定值不值得做——若要做， 检索索引改按变更文件增量更新（最容易切出来）； 领域投票在信号未变的子图上复用上轮结果；trace 只重算受影响入口的可达子图。

影响小 git 信号仍是 sync 后的主要耗时，且 subject 只取最近 4000 条

三级缓存已经把常见路径（HEAD 未动 / HEAD 前移）优化掉了， 但 rebase、force-push、换机器新 clone 之后要回退全量 walk（十年老库要几分钟）。 另外提交 subject 限 4000 条——早期提交里的业务语境会被丢掉， 而老项目最初的设计意图往往恰好在那些最早的提交里。

优化方向：把 git 信号按 commit sha 持久化成可累积的物化视图 （commit 是不可变对象，天然适合永久缓存），使全量 walk 一个项目只需付一次； 这样 4000 条上限也能一并放开。

五、适用范围与工程面

影响中 probe 架构的可扩展性尚未被第二种栈证伪

「换个栈只需加一个 probe」目前是设计意图，不是已验证事实—— 七个 probe 全部服务于同一条 Java/Maven/MyBatis/Dubbo 技术栈。 真正接入 Spring Boot 注解式或非 Java 项目时，很可能发现抽象边界划错了地方 （比如「表」这个概念对无 ORM 的项目就不适用）。

优化方向：拿一个技术栈差异明显的项目做一次真实接入， 用它来校准抽象——这比继续在同一条栈上加功能更能提升工具的通用性。

影响小 MCP 只暴露三个粗粒度工具

search / domains / status 能回答「有哪些领域」「关键词在哪」， 但答不了 AI 实际最常问的那类问题：「这个接口最终动了哪些表」 「这张表被哪些入口写」——而这些答案数据库里已经有了，只是没接出去。 深挖出的领域档案与能力叙述也还没有对应工具。

优化方向：补 trace（入口→表链路）、table_usage（表→写入方）、 capability（入口能力叙述）三个工具。纯接线工作，无新机制。

优化方向的优先级判断

如果只做三件事，按「收益 ÷ 成本」排序应该是：

  1. 让缺失与不确定可见——链路缺失/截断打标记、领域归属给理由与置信度。 不增加任何抽取能力，但把工具从「可能骗你」变成「会告诉你哪里不可靠」，这是知识库可信度的分水岭。
  2. 矛盾检测——注释与代码不符、叙述引用了 L0 里不存在的标识符， 都自动列为待确认。前者是老项目最高价值的产出，后者是幻觉的机械判据。
  3. 补齐 MCP 工具面——数据已在库里，接线成本最低，直接提升 AI 接手的实际效率。

而「扩展增量粒度」「支持更多语言」这类看起来更像正事的工作， 在当前规模（20 秒全量）和当前目标（公司内部 Java 老项目）下， 优先级明显更低——先解决可信度，再解决覆盖面。

10同类开源项目对比

这个方向已经很热闹，但侧重点不同——看清差异有助于判断该自研还是该借。

按成熟度分五类

这个方向的东西很多，但成熟度差得极远——从 1k star 的可安装工具到只有 4 次提交的研究原型都有。 先按能不能真的拿来用分类，再谈思路差异：

第一类：仓库 Wiki 生成器（面向人阅读）

代表是 deepwiki-open（Cognition 的 DeepWiki 的开源实现，把任意 GitHub/GitLab 仓库变成可交互的多语言 Wiki，带 AI 检索与图表）、 OpenDeepWiki（C#/TypeScript， 带 Web 界面、思维导图、翻译队列，并暴露 MCP 端点）、 RepoWiki（CLI/浏览器双入口， Mermaid 架构图，PageRank 排出「从哪读起」的路径，靠 .repowiki-state.json 做增量重跑）、 以及更早的 autodoc （深度优先遍历仓库，逐文件逐目录让 LLM 写文档，已属实验性质）。

差异：这一类基本是「逐文件/逐目录喂给 LLM 写说明」，产出按代码结构组织 （这个文件做什么、这个目录做什么）。CodeAtlas 的产出按业务领域组织， 并且坚持叙述挂证据摘要、证据变了自动失效。换句话说这一类回答「这段代码是什么」， CodeAtlas 试图回答「这个系统在做什么业务」——后者是老项目接手时真正卡住人的问题。 另外这一类普遍不做中文业务术语表，而中文术语 ↔ 代码标识符的映射恰是国内老项目的核心缺口。

第二类：代码知识图谱 / 上下文引擎（面向 AI agent）

代表是 CodeGraph （Rust 内核、20 种语言，预建符号/调用边/依赖图供 agent 一次查询命中， 公布的数据是平均省 35% 成本、少 70% 工具调用）、 Potpie （Apache 2.0，把代码库连同 PR/issue/Notion 等 SDLC 材料一起做成「上下文图」， 配一组预置 agent）、以及研究向的 GraphGen4Code（基于 WALA 静态分析）。

差异：这一类解决的是「让 agent 少花 token 精确定位代码」—— 优化的是检索效率，图里的节点是符号与调用关系，不含业务语义层。 CodeAtlas 与它们不冲突而是互补： 它们让 agent 快速找到代码，CodeAtlas 告诉 agent 这块代码属于哪个业务领域、有什么坑。 事实上本项目所在的开发环境同时装了 CodeGraph，两者各管一段。

第三类：已成工具的学术项目

RepoAgent(OpenBMB,约 1k star、239 commit) 是这一类里唯一真正跨过「论文 → 可用工具」门槛的:pip install repoagent 可装, 有 CLI、GitHub Actions 集成与 pre-commit 钩子,并列出 MiniCPM、ChatDev、XAgent 等采用方。 它的做法是逐对象(类/函数)生成文档并靠 git 钩子在提交时增量更新, 产出仍按代码结构组织,主要面向 Python。

第四类：论文与研究原型（还不是可依赖的工具）

下面这些是论文,不是成熟开源项目——放在这里是因为思路值得借鉴, 而不是可以拿来用。引用它们公布的数据时要记住那是作者自评结果。

  • RepoDoc(中山大学)—— 路线与本项目最接近:先建仓库知识图谱当语义骨架, 再做上下文感知生成与精确增量更新,而且按功能内聚而非物理布局做模块聚类, 与本项目的领域划分思路一致。自评数据:相比 CodeWiki,API 覆盖率 +32.5%、 生成快 3 倍且省 85% token、增量更新省时 73%。 但代码仓库只有约 17 star、4 次提交、 README 只列了几条 CLI 命令——是研究原型,不具备生产可依赖性。 值得做的是读它的聚类与增量更新方法,而不是引入它。
  • Codebase-Memory—— tree-sitter 知识图谱 + MCP 暴露给 LLM,与第二类工具思路重合,论文形态。

第五类：商业产品

Kodesage 专打遗留代码,主打随代码演进的「活文档」、关系映射与可私有化/断网部署—— 定位与本项目几乎完全重合,但闭源、无法按内部技术栈定制。 CodeScene 则是另一个路子:不做 LLM 解读,而是做行为分析, 以「热点」图找出既复杂又频繁变更的代码——它的变更热点思路和本项目用 git churn 当领域信号是同源的。

那么为什么还要自研

四条差异是当前开源项目都没同时覆盖的：

  • 按业务领域而非文件结构组织，且领域是从包路径/表名/git 共变/调用四路信号投票算出来的，不靠人工划分；
  • 叙述强制挂 source_digest，证据变了自动失效——多数 Wiki 生成器是「重跑一遍覆盖掉」，说不清哪条结论该作废；
  • 中文业务术语表（术语 ↔ 别名 ↔ 代码标识符 ↔ 枚举值），针对国内老项目「注释是中文、标识符是拼音或英文缩写」的现实；
  • 咬住特定老技术栈的脏细节：MyBatis resultMap 反推表结构（项目连 DDL 都没有）、 ON DUPLICATE KEY UPDATE 特判、Dubbo XML 入口、接口→实现的 override 边 （补上这条链路从 4 条变 455 条）。通用工具不会为一条内部技术栈做这些特判，而老项目的知识恰恰卡在这些细节上。

反过来说，不该自研的部分也很清楚：符号级检索与调用图定位， CodeGraph 这类工具做得更好且支持 20 种语言，直接共用即可； 逐对象的 API 级文档生成，RepoAgent 已经做到可安装可集成。 这两块没必要在 CodeAtlas 里重做——它该守住的只有「业务领域划分 + 证据可追溯的中文业务叙述」这一段。

一个需要诚实承认的点：上述项目大多有社区、有多语言支持、有基准数据， 而 CodeAtlas 目前只在一个项目上验证过。它的价值在于对特定老技术栈和中文语境的贴合度， 以及证据可追溯这一机制约束——不在通用性。 如果目标项目换成技术栈现代、文档尚存的库，成熟开源方案大概率更划算。

一句话总结

CodeAtlas 把老项目里确定能抽出来的事实（注释、表结构、git 历史） 先零成本地全量沉淀成结构化真相，再让大模型只在这些证据之上写业务叙述， 并给每条叙述挂上证据摘要——于是文档天生可追溯、可审计， 并且会随代码自动失效重算，而不是随时间腐烂。
