CodeAtlas · 改进建议

对照同类项目，CodeAtlas 还该改什么

核心机制文档第 09 节的优化方向是从内部缺陷推出来的； 这份是从外部对照推出来的——把 RepoAgent、RepoDoc、CodeGraph、Potpie、 RepoWiki、CodeScene 这些项目已经解决的问题，逐条对回 CodeAtlas 的现状。

目录

  1. 结论先行：该借什么、不该借什么
  2. 结构性缺口（别人解决了，我们没有）
  3. 低成本改进（数据已在库里）
  4. 被同类项目反向印证的设计
  5. 明确不该借的部分
  6. 落地顺序

A结论先行：该借什么、不该借什么

把六个参照项目的差异过一遍后，可归纳成三句话：

  1. 最该补的是「让文档自己保持新鲜」的触发机制。 CodeAtlas 有一整套 digest 失效判定，但没有任何东西会去触发它—— 没人主动跑 catlas sync，失效判定就等于没有。RepoAgent 用 git 钩子解决了这件事。
  2. 最该补的第二件是「知识不止在仓库里」。 CodeAtlas 只读代码 + git，而 Potpie 还索引 PR、issue、Jira、Notion。 老项目里「为什么这么做」的答案大量躺在需求单和 PR 讨论里，这是我们目前拿不到的一整类证据。
  3. 最该抵制的是「把自己做成通用工具」。 CodeGraph 支持 20 种语言、RepoAgent 已有 1k star，在通用性上追是稳输的。 CodeAtlas 的立足点是对特定老技术栈与中文语境的贴合度，扩语言优先级应当排在最后。

B结构性缺口

这些不是「做得不够好」，而是整类能力的缺失——别人有，我们没有。

优先做 B1 · 没有任何机制触发更新，失效判定形同虚设 对照 RepoAgent
现状
已核实：代码里没有任何 hook / CI / Actions 集成，仓库也没有 .github/。 整条链路是「人想起来 → 手动跑 catlas sync → 手动跑 catlas render」。
别人怎么做
RepoAgent 提供 pre-commit 钩子与 GitHub Actions 集成，提交即更新文档； RepoWiki 用 .repowiki-state.json 记录状态，重跑只重算源文件变了的页面。
为什么这是最要紧的一条
第 04 节把「文档不腐烂」归功于 source_digest 自动失效—— 但严格说这只做到了「能判定哪条过期」，没做到「会去判定」。 没有触发器，半年后库里仍是半年前的快照，与手写文档腐烂的结局并无区别。 这是全项目投入产出比最高的一处缺口：机制早已齐备，缺的只是一个触发点。
建议
加 catlas hook install，装一个 post-commit（而非 pre-commit：避免拖慢提交）钩子后台跑 sync； 再给一份 CI 模板，在 CI 里跑 sync 并把「新增的 stale 条目数」作为报告输出。 不必自动调 LLM 花钱——只要把「哪些结论已过期」持续暴露出来，人就知道何时该深挖。
值得做 B2 · 只读仓库，拿不到 PR / issue / 需求单里的业务语境 对照 Potpie
现状
已核实：证据源只有源码、配置、git 提交。不摄取 PR、issue、工单、文档系统。
别人怎么做
Potpie 把代码连同 PR、issue、review、Linear/Jira、Notion/Confluence 一起做成「上下文图」， 理由正是：决策的「为什么」不在代码里。
为什么对老项目尤其重要
第 09 节承认了一个根本局限：「没留痕的业务规则抽不出来」。 但更准确地说——很多规则其实留了痕，只是痕迹不在仓库里， 而在 PR 的争论、工单的验收标准、review 的追问里。这不是模型能力问题，是证据源覆盖问题， 属于可以工程解决的那一类。
建议
按 probe 架构加一个可选的外部证据 probe，先只做最容易拿且信息密度最高的一种 （内部 GitLab/GitHub 的 MR 标题 + 描述 + 关联工单号）， 与 commit subject 同层存放并标注来源。 注意两点：这类源的可靠性低于代码，必须区分置信度；且涉及把内部工单内容并入知识库， 需要先确认合规边界。
值得做 B3 · 只在一个项目上验证过，且没有任何可比较的指标 对照 CodeGraph / RepoDoc / RepoAgent
现状
验证材料是：127 个单测（覆盖确定性部分）+ 一个项目的构建统计 + 一个领域的人工抽查。 没有任何可对外比较的质量或效率指标。
别人怎么做
这个领域已经收敛出一套通行度量：CodeGraph 报「省 35% 成本、少 70% 工具调用、快 49%」； RepoDoc 报「API 覆盖率 +32.5%、省 85% token、增量更新省时 73%、更新召回率 +10.2%」。 它们都是作者自评，但至少是可被质疑、可被复现的数字。
建议
不必追论文式的完整评测，选两个能自测且直接对应价值主张的指标即可： ① token 成本——每个领域深挖的实际花费，让「按需深挖」这个卖点可被定价； ② agent 工具调用削减——同一组业务问题，接 MCP 前后 Claude Code 的工具调用与 token 对比。 第二个指标同时能回答「这东西到底有没有用」这个绕不开的问题。

C低成本改进

共同点：所需数据已经在库里，只是没接出去或没渲染出来。

优先做 C1 · 没有「从哪读起」的入口路径 对照 RepoWiki
现状
渲染产出 43 个领域档案，但不排优先级。 已核实 churn 目前只用于领域投票和源码节选，没有用来给领域排序。 新人打开 .knowledge/ 面对 43 个平铺的领域，仍然不知道先看哪个。
别人怎么做
RepoWiki 用 PageRank 算出一条「start here」阅读路径。
为什么我们能做得更好
PageRank 只看引用结构，而 CodeAtlas 手上的信号更贴业务： 入口数量、链路条数、churn、领域规模、涉及表数。 加权排个序就能给出「这个项目最该先理解的 5 个领域」—— 这恰恰是接手者的第一个问题，而现在文档没有回答它。
建议
README 顶部加「建议阅读顺序」小节，列前 5~8 个领域并给出入选理由（入口多 / 改动频繁 / 表多）。
优先做 C2 · MCP 工具面太窄，库里已有的答案没接出去 对照 CodeGraph / Potpie / OpenDeepWiki
现状
只有 search / domains / status 三个工具。
缺口
AI 接手老项目最常问的恰恰是三个库里已有答案的问题： 「这个接口最终动了哪些表」（traces 表里有）、 「这张表被哪些入口写」（反查即得）、 「这个领域有什么坑」（深挖出的 landmines 已存在）。 另外 CodeGraph 那组「省 70% 工具调用」的收益，前提是工具能一次答到点上—— 工具面窄就等于把 agent 推回去 grep。
建议
补 trace、table_usage、capability、domain_dossier 四个只读工具。 纯接线，无新机制，是整份文档里最便宜的一项。
值得做 C3 · 没有任何图，而链路数据天然适合画图 对照 RepoWiki / deepwiki-open / GitDiagram
现状
已核实：渲染层不产出任何 Mermaid 或图表，全是文字与表格。
为什么成本很低
455 条「入口 → … → 表」链路和领域间的调用关系已经是图结构， 转成 Mermaid 只是换个输出格式；而 GitLab、GitHub、VS Code、Obsidian 都原生渲染 Mermaid， 不需要任何额外设施。
建议
领域档案里嵌两张：领域间依赖图、以及该领域核心入口的链路图（节点数需设上限，否则会糊成一团）。 不做交互式大图——那属于产品化投入，与「给 agent 用」的定位无关。
可选 C4 · 没有独立的问答入口，非 Claude Code 用户无从使用 对照 deepwiki-open / autodoc / Potpie
现状
catlas query 是关键词检索，不是问答。 「这个系统的优惠券怎么算」这类问题必须经 Claude Code 走 MCP 才能回答。
取舍
这其实是有意为之的设计：问答循环交给 Claude Code，工具只当数据源，避免重复造壳。 唯一的实际损失是没装 Claude Code 的人用不上。 建议排在末位——真要做也只是「检索 + 拼证据 + 调一次 LLM」的薄封装（catlas ask）， 而不是自建 Web 界面。
可选 C5 · churn 只当了领域信号，没产出「风险地图」 对照 CodeScene
机会
CodeScene 的立身之本是「热点」——既复杂又频繁变更的代码。 CodeAtlas 已经有每文件 churn、也有领域划分， 两者一交叉就能得到一个别人给不出的产出：哪个业务领域风险最高 （改动最频繁 × 链路最长 × 表最多 × 无人留注释）。
为什么值得
这不是从别人那里补短板，而是用已有数据换一个新视角： 从「这个系统在做什么业务」延伸到「这个系统哪块最危险」—— 对接手者的决策价值很高，且几乎不增加抽取成本。排在可选是因为它不解决现有缺陷，属于加分项。

D被同类项目反向印证的设计

对照的另一半收益：确认哪些地方不用改。

增量更新优于全量重生成——RepoDoc 用数据证实了这一点。 它报告增量更新的召回率比全量重生成高 10.2%。这个结果值得留意： 直觉会认为全量重算更准，但全量重算会让每条结论重新承受一次 LLM 随机性， 已经正确的结论可能被改坏。CodeAtlas 的 digest 失效 + 稳定键 relink （只重算证据变了的条目、其余原样保留）正好落在被证实更优的一侧， 不必因为「全量更彻底」而动摇。

按功能内聚而非物理布局聚类是对的。 RepoDoc 独立得出了同一结论（module clustering by functional cohesion）。 这说明「包结构不是业务边界」不是我们一个项目的特殊观察，而是这类工具的共识。

MCP 是正确的接入面。 CodeGraph、Potpie、OpenDeepWiki、Codebase-Memory 全都走 MCP。 选型上无需再犹豫，要补的只是工具数量（C2）。

E明确不该借的部分

对照最容易犯的错，是把别人的长处当成自己的待办。

别人的能力为什么不该追
多语言支持
CodeGraph 20 种语言		 目标是公司内部 Java 老项目。扩语言会摊薄唯一的优势（对特定老栈脏细节的贴合）， 且第 09 节已指出 probe 抽象尚未被第二种栈检验——先用一个真实异构项目校准抽象，再谈扩展。
符号级检索与调用图定位 CodeGraph 做得更好。它与 CodeAtlas 是互补关系（一个找代码、一个讲业务）， 重做只是浪费。更划算的方向是反过来消费它： 加一个可选 probe 直接读 CodeGraph 的索引，省掉自己的部分解析。
逐文件 / 逐对象 API 文档
RepoAgent、autodoc		 产出按代码结构组织，正是 CodeAtlas 刻意不做的那一类。老项目缺的不是「这个方法做什么」 （看代码就知道），而是「这属于什么业务、有什么坑」。
Web 界面、多语言翻译、思维导图
OpenDeepWiki、deepwiki-open		 产品化投入，与「人读 Markdown + agent 走 MCP」的定位正交。 投进去的时间从可信度改进里挪走，不划算。
覆盖 SDLC 全域
Potpie 的 Notion/Linear/Jira		 值得借的只是 B2 里那一条最小切口（MR 描述 + 工单号）。 全域接入会把工具变成平台，偏离「一个能进 CI 的 CLI」这个形态。

一条贯穿性的判断：这些项目在覆盖面上都比 CodeAtlas 强， 而 CodeAtlas 唯一可能领先的是特定场景下的可信度—— 叙述挂证据、失效可判定、领域按业务划分、咬住老栈脏细节。 所有优先级都该照这个方向排：凡是提升可信度的排前面，凡是扩大覆盖面的排后面。

F落地顺序

顺序事项为什么排这个位置
1 MCP 补四个工具（C2） 数据已在库里，纯接线。立刻提升 agent 实际可用性，且是验证指标（B3）的前提。
2 更新触发机制：hook + CI（B1） 失效判定已建好却没人触发，是整个「不腐烂」主张的唯一缺环。成本低，收益是结构性的。
3 建议阅读顺序（C1） 一次加权排序即可，直接回答接手者的第一个问题。
4 两个自测指标（B3） 接 MCP 前后的 token / 工具调用对比。没有它，后续改进无从判断好坏。
5 Mermaid 图（C3） 图数据已有，换输出格式而已；但属体验改进，让位于前四项。
6 MR / 工单证据 probe（B2） 唯一能突破「证据源覆盖」这层天花板的一项，但牵涉外部系统与合规确认，宜在基础稳固后做。
7 风险地图（C5）、catlas ask（C4） 加分项，不解决现有缺陷。

与第 09 节优化方向的关系：那一节的头两项（让缺失与不确定可见、矛盾检测） 仍应排在本表之前——它们修的是「文档可能骗你」这个根本问题， 而本表大多是「文档还能更好用」。 顺序是：先让它不骗人，再让它自动保鲜，最后让它更好用。
